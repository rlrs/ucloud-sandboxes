# Remaining cache miss: tools case 022

The single-import burst completed all 48 builds. Case 022 (`typescript-tools`, `app-change-12`) still spent 33.629 seconds building/pushing, including 8.6 seconds materializing its cached parent, 3.6 seconds copying source and 19.9 seconds running the application build. Its 54.637-second client completion drove the 54.656-second batch duration. The other 47 builds finished at roughly 22 seconds. This remaining miss does not invalidate the measured improvement, but it prevents a claim of universal warm-build reuse.

The selected tools cache was complete. Four exact owned cache manifests and their small config blobs were fetched with GET only, bounded to 1 MiB per response and verified against manifest/config digests. The prior tools export and new tools export contain the same 13 graph records, dependencies and selectors. Both final COPY and application RUN already had materializable result blobs in the imported cache; the new build replaced those results with new blobs and timestamps. Source changes or an incomplete tools export therefore do not explain this miss. Digests and comparison evidence are saved in [case22-outlier.json](case22-outlier.json).

Case 023, the multistage build of the same application variant, started on the same builder 318 milliseconds before case 022. Their build phases overlapped. The tools log labels its final COPY/RUN as `compile`, the stage name from the multistage Dockerfile; the multistage log also includes materialization progress from the tools solve. The multistage cache contains all 13 matching tools graph records but no result blobs on the shared final COPY/RUN records. Its final image is cached and its imported/exported cache-config digests are identical. Among the four same-variant tools/multistage pairs assigned to the same builder, this was the only pair whose estimated build phases overlapped, and the only tools outlier.

BuildKit v0.33.0 shares active vertices by graph digest and adds each job's cache sources to the shared state. Consequently, one explicit import per request does not guarantee that a shared active vertex sees only one imported cache. This directly fits the overlapping logs and graph metadata. [BuildKit solver state and cache-source handling](https://github.com/moby/buildkit/blob/v0.33.0/solver/jobs.go)

The combined cache query retains one returned cache-key object per key ID; result lookup then uses the cache-manager identities attached to that object. Competing complete and partial records are a plausible mechanism for this remaining miss, but the live run did not trace that internal decision. The established conclusion is a shared-graph interaction, not a proven upstream bug fix. [BuildKit combined-cache implementation](https://github.com/moby/buildkit/blob/v0.33.0/solver/combinedcache.go)

The bounded next diagnostic is the exact tools/multistage pair on a fresh private daemon, using these immutable cache digests and one import per solve. Compare sequential execution with simultaneous and 300-millisecond-staggered execution, then repeat the overlapping pair on separate private daemons. Keep output/cache export disabled and verify application output in a separate semantic check. This isolates cross-recipe graph sharing without changing production scheduling or fixtures. If reproduced, test a complete multistage `mode=max` cache in an isolated repository or a focused upstream cache-manager fix before considering a daemon pool; both require fresh correctness and resource measurements. No additional runtime change was made for this outlier.

Build-phase overlap is estimated from execution timestamps and recorded build/push duration; preparation and mount work slightly shift actual solve starts. Shared progress can label a pruned intermediate as cached without providing a remotely materializable intermediate result. Neither that label nor the correlated timing alone proves the exact internal failure path.
