# Shared image foundations

The foundation workflow publishes an expensive, task-independent Dockerfile prefix once, converts it to signed EROFS components, and retains the image and component manifests. Task recipes then use its immutable registry digest in `FROM`. Builders can reuse it after BuildKit cache eviction or builder replacement.

The component layout is part of each layer group's key. After builders switch to layout 2 ([file mtimes](immutable-environments.md#file-mtimes-layout-2)), republish each foundation before its task images. Task publication then finds the foundation's layout-2 base components, including its last, partly filled group. Layout-1 foundation components stay valid for images that are not republished.

Supported prefixes are the explicit TMax `base_install.sh` stage, conservative literal initial apt/pip commands in monolithic TMax installers, the Python/Conda prefix generated by the pinned OpenSWE index tooling, and context-free initial Terminal-Lego dependency instructions. Source checkout, project installation, fixtures, and subsequent task commands remain in their original order.

## Plan and build

Resolve a linux/amd64 upstream manifest digest first. Use a fresh output directory and the exact source revision being prepared:

```sh
uv run python scripts/plan_image_foundations.py plan \
  --tmax-root /data/prime-tasks/datasets/tmax \
  --ubuntu-base 'ubuntu:22.04@sha256:<resolved-manifest>' \
  --source-revision '<prime-tasks-commit>' \
  --output /data/tmax-foundations

uv run python scripts/plan_image_foundations.py plan-openswe \
  --recipes /data/openswe_oss.jsonl \
  --miniconda-base 'continuumio/miniconda3:25.3.1-1@sha256:<resolved-manifest>' \
  --source-revision '<dataset-commit>' \
  --output /data/openswe-foundations

uv run python scripts/plan_image_foundations.py plan-tmax-inline \
  --tmax-root /data/prime-tasks/datasets/tmax \
  --ubuntu-base 'ubuntu:22.04@sha256:<resolved-manifest>' \
  --source-revision '<prime-tasks-commit>' \
  --output /data/tmax-inline-foundations
```

The planner ranks foundations by source-recipe count. Counts are preparation candidates, not the actual training selection or a promise that every unusual Dockerfile can be rewritten. Foundation identities include the pinned Dockerfile, platform, and installer content; they exclude local paths and task-specific files.

For Terminal-Lego, supply a JSON mapping from literal source base to its verified `reference` and `onbuild` values returned by `prepare_image_pool.resolve_source`. The resolver verifies the manifest, image-config digest and platform. Missing or nonempty inherited ONBUILD triggers are rejected: such a base might otherwise consume task context during the foundation build.

```sh
uv run python scripts/plan_image_foundations.py plan-terminal \
  --terminal-root /data/Terminal-Lego-15k \
  --pins /data/verified-terminal-base-pins.json \
  --source-revision '<dataset-commit>' \
  --limit 1000 --output /data/terminal-foundations
```

Terminal prefixes stop before COPY, ADD, ARG, RUN mounts/heredocs, or unrecognized instructions. Custom frontends, multiple/named stages, and context copies outside the pinned task-file/verifier-script layout are not factored. Broad copies that could include the rewritten Dockerfile are rejected. Literal RUN commands and their preceding ENV/WORKDIR/USER/SHELL settings retain their order; comments do not prevent sharing. The new index preserves task context, file overrides, leading canary comments, and all remaining Dockerfile bytes. Verifier bootstrap and task-specific dependency commands after the context boundary still need preparation. Recipes modified into multiple stages by verifier certificate isolation remain unchanged.

Copy a plan directory to the gateway. Run the preparation script as the gateway service account, with a compatible SDK wheel and the existing deployment configuration:

```sh
python scripts/prepare_image_foundations.py \
  --root /data/tmax-foundations \
  --sdk-wheel /data/ucloud_sandboxes_sdk-0.4.34-py3-none-any.whl \
  --config /etc/ucloud-sandboxes/deployment.json \
  --gateway https://sandbox.example \
  --limit 1
```

The runner processes at most `--limit` foundations, with `--workers 1` by default and a maximum of 32. Upload `prepare_image_pool.py` alongside it for shared storage-admission helpers. `--growth-limit-gib` (default 128), `--free-floor-gib` (300), and `--reservation-gib` (8 per pending build) bound admission against current registry usage; reservations are estimates, not filesystem quotas. The growth baseline persists across restarts. Failed or deferred foundations are recorded separately while other entries continue; only validated artifacts enter the ready catalog. Per-foundation result journals recover catalog updates after interruption, and shared claims prevent duplicate concurrent submissions across plan directories. It hashes the context before submission, records accepted build IDs, checks published artifacts before consulting old build history, and resumes the same accepted build. It validates signed environment metadata, protects the transitive artifact closure using persistent `image-foundation:<key>` owners under the gateway's GC lock, and runs a bounded smoke sandbox. Only validated results enter the `foundations` section of `catalog.json`; a validated unchanged artifact can be resumed without repeating its smoke. Temporary validation sandboxes are deleted and also have a finite TTL.

TMax validation imports the scientific libraries and verifies CPU-only PyTorch. OpenSWE validation checks the selected Python and SSL runtime. Terminal prefixes check filesystem mount/exec after successful dependency installation. These checks establish foundation usability; they do not replace qualification of task-specific build operations.

Upstream installers contain unpinned packages. The published artifact freezes their resolved result. Reuse its catalog rather than rebuilding the same plan to obtain newer packages. An intentional refresh should change the pinned inputs or Dockerfile preparation version and produce a new identity.

## Use the foundation catalog

Write a new recipe database and select it through the integration's existing `image_recipe_db` setting:

```sh
uv run python scripts/plan_image_foundations.py rewrite-index \
  --source /data/images.sqlite \
  --catalog /data/tmax-foundations/catalog.json \
  --catalog /data/openswe-foundations/catalog.json \
  --output /data/images.with-foundations.sqlite
```

This accepts only validated matching foundations. TMax matches the complete explicit base prefix and installer bytes. OpenSWE matches the exact generated Python prefix, allowing leading ordinary comments and blank lines; custom frontend directives, intervening instructions, and unmatched layouts are left alone. No project-dependent installation is moved ahead of its source.

For monolithic TMax scripts, the matcher accepts only literal leading package commands and supported initial shell options. It stops before local requirements, substitutions, redirects, source operations, or unrecognized statements; scripts observing prior command status are rejected. It preserves shell options and the task remainder, and places the rewritten `post_install.sh` in the recipe's existing `files` overrides. Real task equivalence must be qualified in addition to the foundation smoke. Do not assume package-version stability when intentionally refreshing a foundation built from unpinned upstream packages.

Rewritten rows clear their old `prepared_image`, because that name belongs to the original recipe identity. Other families and unmatched recipes retain their original records. The source database is opened read-only; the destination is published atomically without replacing an existing file. The current integration and SDK can consume the resulting recipes without a new SDK release.

Foundations alone do not make every task image ready. Use the normal bounded image-preparation workflow for the resulting task recipes. A task delta can still require package installation, source compilation, or Docker materialization for unsupported selective EROFS conversion. Keep the foundation catalog and per-task prepared-image manifest distinct.

Persistent foundation references deliberately survive opportunistic cache pruning. Retire them explicitly once no active preparation catalog needs them, using the registry's existing reference-release mechanism. Do not delete the shared component blobs directly.

For retained external task images, mixed-family batches, import aliases, and storage admission, see [image-pools.md](image-pools.md).

## Reusing already prepared upstream bases

Pass `--base-catalog /data/source-pool/catalog.json` (repeatable) to the foundation preparer. It accepts only ready, faithful source preparations whose immutable upstream digest exactly matches the foundation's base. Enriched preparations are excluded. A separate execution context replaces just that FROM operand with the prepared private artifact; canonical dependency contexts and remaining installer bytes stay unchanged. Existing accepted jobs resume before any new job is submitted. Use `--retry-recorded-failures` to retry a recorded failed or missing job with the locally prepared base.

The current catalogs contain exact bases for all 2,786 planned TMax-inline and 5,804 Terminal-prefix foundations. Their base acquisition need not contact Docker Hub. Dependency RUN commands may still contact apt, pip or other package services; this option does not make those commands offline. Verify a canary and preserve the new catalogs before switching a task index.

Keep `stage_source_image.py` beside the preparer. Before a new submission it verifies the pinned base manifest and pre-links existing layer blobs into the managed output and BuildKit cache repositories, within a three-second optional preparation budget. `source_mounts` in the receipt records the result. This changes neither the canonical foundation recipe nor BuildKit's input validation.
