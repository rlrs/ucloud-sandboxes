# 256-sandbox qualification, September 19

The first production run started 256 creates concurrently from an empty fleet,
using server 0.5.36 and SDK 0.4.20. All created in 78.4 seconds across two workers
(128 each). All 256 managed Python agents then passed upload, execution, and
byte-exact download checks in 15.6 seconds. The first simultaneous park burst
failed for 20 callers with a broken pipe, while 236 succeeded. Test resources
were deleted successfully. The retained summary is
[concurrency-256-0536-2026-09-19.json](../benchmarks/concurrency-256-0536-2026-09-19.json).

The HTTP connection limiter sent its structured safe-retry response immediately
on accept and closed the socket without reading the request. When the client
was still writing POST headers/body, it could receive a TCP reset/broken pipe
before it read that response. The client correctly does not replay arbitrary
ambiguous transport errors. A delayed-body regression reproduces BrokenPipeError
with the old rejection implementation.

Server 0.5.37 half-closes the response and uses a nonblocking selector to discard
incoming bytes. Rejected sockets never occupy request threads or block the
accept loop. Retention is bounded to two seconds, the HTTP backlog size, and
16 MiB plus header allowance per socket. This preserves safe-retry responses for
ordinary overload races without an unbounded thread or request-body queue.
Very slow or oversized rejected senders still reach those explicit bounds.

The regression also checks that another client receives its rejection while the
first sender pauses mid-body. A separate test proves abandoned sockets expire.
The canonical checks passed 894 server tests (six skipped), 99 SDK tests, lint,
shell checks, Go tests, package builds and installed-wheel checks.

## Second run and follow-up

Server 0.5.37 deployed at 04:51:34 UTC. Its 256-way run used the original
workload shape: 2 vCPU, 1024 MiB RAM and 5184 MiB disk per sandbox. All 256
created in 79.4 seconds, initialized and executed tools in 14.1 seconds, and
parked in 8.7 seconds. The first resume/upload/tool burst passed 254 and failed
two. Cleanup succeeded. See the
[0.5.37 result](../benchmarks/concurrency-256-0537-2026-09-19.json).

One upload received nginx HTML 502. Its final retained gateway trace
`81c7715a1101fd691581fc44907b8521` contains a single 4.3-ms gateway span with
status 503 and no downstream dispatch, consistent with another unread-body
rejection being lost on connection close. Handler-level admission used a
different close path from the thread-cap rejection. Version 0.5.38 applies
bounded socket draining to completed handlers too, with a lock protecting
selector registration from concurrent request threads. A delayed-body test
now covers this path.

The other failure was a storage-device capacity rejection during explicit wake
(trace `a062502d5658703401b95ad49f546841`). A newly restored route stopped
reserving its device as soon as it became running, even if the heartbeat still
showed it parked. Version 0.5.38 retains that reservation until the heartbeat
observes the restored owner. Typed capacity failures during explicit wake are
safe-retry responses only when the node confirms the lifecycle remains parked;
unknown, restoring and running outcomes remain ambiguous.

The full-device heartbeat also outlived the park burst and prompted unnecessary
publication before the next periodic heartbeat. Worker telemetry counted 24
publications and about 5.8 GB uploaded during this cycle. Before moving work
away from an apparently full owner, 0.5.38 refreshes its authenticated heartbeat
outside placement locks. Refreshes are coalesced per worker and limited to once
per two seconds, with identity/epoch validation and normal heartbeat receipt
fences. Other callers safely defer while a refresh is active. This avoids
subtracting guessed device releases from inconsistent metrics.

The 0.5.38 server suite passed 897 tests (six skipped). The first full check
hit an intermittent interruption-cleanup assertion in the existing benchmark
fake; the isolated test and the unchanged full rerun passed. No production
cleanup failure occurred in either live run.

## Relay transport and SDK 0.4.21

A subsequent 256-agent test exercised real public relay HTTP requests, automatic
parking, response commits, resumed agent execution, and a subprocess tool check.
With SDK 0.4.20, all agents started and parked, but 28 commits failed (20 broken
pipes and eight disconnected responses). The idempotent commit helper only
retried 503 responses. SDK 0.4.21 also retries transient transport/HTTP failures,
retaining the exact lease, request identity, and reply bytes. It never repeats
the upstream model call. Terminal registration/lease errors and explicit
non-retryable responses still stop immediately.

A second attempt exposed a broken pipe during agent startup, where retrying an
ambiguous execution request is unsafe. Direct public gateway and relay probes
both measured idle socket EOF at 10.0 seconds. The async clients used aiohttp's
15-second idle retention. SDK 0.4.21 retires its owned connections after five
seconds to avoid that mismatch; injected sessions retain caller ownership and
settings. A local HTTP regression verifies reuse while recent, replacement
after idle expiry, and session ownership. This mitigates the observed race;
it does not make arbitrary transport failures safe to replay.

SDK commit `f50c6114228bee13524af7c053b74fc36f86d33b` passed the canonical
checks: 897 server tests (six skipped), 106 SDK tests, lint, shell and Go checks,
builds, and installed-wheel checks. Its wheel SHA-256 is
`d38776b88b38e3a710ad659cf4c813f53c222cff63e0560e219b85a213ed8dbe`.

The packaged SDK then passed all 256 cold creates in 76.8 seconds on fresh
0.5.38 workers `12396306` and `12396307`, 128 each. All 256 relay agents
initialized in 5.5 seconds. Each of three cycles confirmed all 256 were parked
before releasing the replies. Reply commit and wake bursts took 28.8, 27.0,
and 30.5 seconds; all 256 agents consumed the correct response, retained their

These relay tests use controlled HTTP echo replies, with no external model

## Shared relay worker starvation

The per-rollout client test was insufficient to qualify the published Verifiers
interception, which shares one AsyncRelayWorkerClient. With 256 SDK `run_worker`
loops (10-second polls, max concurrency eight per rollout), the single default
100-connection pool starved forwarding entirely: 100 requests were leased,
156 remained pending, and zero HTTP requests reached the controlled upstream
within the 120-second verification budget. All 256 tool checks timed out.
The gateway remained healthy (184 probes, zero failures); test cleanup succeeded.
See the [failed shared-pool test](../benchmarks/concurrency-256-0538-relay-shared-pool-failure-2026-09-19.json).

SDK 0.4.21 now separates owned polling, upstream forwarding, and control pools.
Their connection limits are respectively 512, 100, and 100. Long polling and slow
model requests cannot occupy the connections used to commit replies or renew
leases. Caller-supplied sessions keep their own pooling policy. All owned pools
close with the client.

A local regression holds 100 polls and 100 upstream requests open, then checks
control responsiveness and commits all 100 replies before releasing the polls.
The old single-pool topology fails by timeout; the separate pools pass. The
canonical check passed 897 server tests and 107 SDK tests, plus lint, builds,
Go/shell checks, and installed-wheel checks.


## Completed-request renewal race

After pool isolation, the shared-worker test passed two full 256-agent cycles,
including exact response consumption and resumed tool execution, but failed
168 checks in cycle three. Those 168 SDK workers had exited on renewal HTTP 410
`request is already completed`. Exactly 256 upstream calls ran in each of the
first two cycles and 88 in the third; no retry repeated a model call. All 320
health probes passed, and cleanup succeeded. The
[failed result](../benchmarks/concurrency-256-0538-relay-renewal-failure-2026-09-19.json)
is retained.

A response is committed before the relay finishes waking its caller. Lease
renewal can therefore observe completion while the response POST is still in
flight. The SDK propagated that renewal error even after its own commit had
succeeded, terminating the whole rollout. Both sync and async handlers now
ignore only the specific already-completed renewal error after successful
response handling. They still propagate failed commits, invalid/expired leases,
and other HTTP 410 responses. Regression tests exercise both the benign race
and those failure boundaries.


## Linux-host live-process capacity

The published Verifiers runtime uses `SandboxSpec.benchmark()` (the Linux-host
profile) and `open_process()`. It does not request managed-process parking.
The managed-agent tests above therefore do not substitute for this profile.
A separate 256-way test created all Linux-host sandboxes, then started a live
process in each and performed concurrent uploads, exec, and downloads. Server
0.5.38 failed 174 initialization/tool checks, including HTTP admission exhaustion,
missing exec sessions, and two nginx 502 responses during exec POSTs. Twelve
health probes failed under this load. Cleanup succeeded. The
[Linux-host failure](../benchmarks/concurrency-256-0538-linuxhost-failure-2026-09-19.json)
is retained.

Each live process holds an exec-event long poll. The production gateway limit
was 128 HTTP threads, below the number of active streams alone. Nodes also
allowed only 128 total exec sessions: 128 resident agents left no room for tools,
and completed tool results could be evicted before callers read them.

Server 0.5.39 raises the bounded HTTP capacity to 768 at the gateway and 512 per
node, reserving headroom for 256 agent streams, tool streams, and other requests.
Heavy startup admission remains 32 globally and eight per worker. Exec session
capacity becomes 1024 per worker, and completed results cannot be evicted under
pressure until at least 30 seconds old. When all slots are occupied, admission
returns a typed safe-retry response before starting a process. Regressions check
result retention, no process dispatch on rejection, lease cleanup, and the HTTP
retry contract. SDK exec-event reads also retain the caller's retry deadline
instead of stopping after sixteen explicit admission rejections.
