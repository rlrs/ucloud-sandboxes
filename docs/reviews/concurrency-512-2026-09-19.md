**512 concurrent sandboxes passed the Linux-host and managed relay profiles.**
Server **0.5.44** is deployed; SDK **0.4.22** is published and pinned in the
Verifiers integration. All changes are committed and pushed. Qualification
uses lightweight Python agents and a controlled echo upstream, not 512
simultaneously CPU- or memory-saturated workloads or an external model service.

round and either stalled on the next barrier or missed the deadline. The final

version 0.5.44, startup concurrency eight, restore concurrency twelve, HTTP

The existing 32-vCPU workers will use 12 concurrent restores, up from eight.
Create/startup admission remains eight per worker and 32 globally. Active

The restore setting is a production configuration change, subject to live

rejected. Caller-supplied sessions keep their transport policy and ownership.

The local regression holds 512 polls and 512 upstream requests simultaneously,
checks control responsiveness, then verifies all 512 replies commit while polls
remain open. Other tests cover custom limits, environment overrides and invalid
values. The full checks passed 902 server tests (six skipped), 113 SDK tests,

## Relay lifecycle dispatch

Inspection found another throughput bottleneck: the relay used `asyncio.to_thread`
for blocking park/wake HTTP calls. On the two-core production gateway, the default
executor admits only six operations together. Increasing node restore slots alone
could not remove this shared bottleneck.

Server 0.5.42 uses separate bounded pools for park (16) and wake (48). Async
semaphores bound submission; cancellation holds its slot until blocking work
finishes. Request tracing context follows work into the dedicated threads.
Cleanup waits for both pools to shut down. The existing lifecycle generation,
idempotency, retry and response handling remain intact. A regression saturates
the park pool, cancels an active caller and verifies admission remains bounded,
while 48 wakes complete independently using the original tracing context. A
second test checks failure propagation and slot reuse. Full checks passed 904
server tests (six skipped) and 113 SDK tests.

## Runner descriptor limit discovered at 512

The first 512 Linux-host run created all sandboxes in 262.2 seconds and passed
all initial live-process/tool checks in 26.7 seconds. Its first repeat round
then hit `EMFILE` in the load generator: the interactive shell inherited a
1024-descriptor soft limit. Persistent agent sockets plus concurrent tool/file
connections exhausted it. The same limit prevented writing a progress file,
so that failed result's phase aggregation is incomplete; failure events are
retained separately. All 288 health probes passed and all 512 sandboxes were
cleaned up. Both services already have `LimitNOFILE=65536`.

[Failed runner result](../benchmarks/concurrency-512-0542-runner-fd-failure-2026-09-19.json).
The rerun explicitly uses an 8192-descriptor soft limit and records it in the
artifact. The Verifiers integration now performs this preparation once at
runtime/interception startup, only raising the soft limit within the existing
hard limit. It never lowers a limit or raises the hard limit. Restricted hosts
receive an actionable warning while smaller runs remain usable. Tests cover
finite/infinite limits, no reductions, failure handling, and one-time behavior.

## Shared relay polling at 512

The initial 512 relay test with the candidate's 1024-poll connection pool failed
to park every sandbox within its 180-second barrier: 511 parked and one still
running at expiry. All test resources cleaned up; no worker exception occurred.
The application logged no relay errors, but only 491 upstream requests had
started, and the relay had roughly 1020 established inbound connections while
using little CPU. This indicates connection pressure in the request/poll path;
it does not identify a specific provider proxy limit. All 308 gateway health
probes passed, illustrating why gateway-only health is insufficient for relay
qualification.

[Retained failed relay run](../benchmarks/concurrency-512-0542-relay-poll-failure-2026-09-19.json).

The SDK candidate now bounds polling to 128 connections and rotates workers
through the pool, shortening idle server waits as shared worker count rises
(about a four-second full rotation, one-second polls at 512). Forwarding retains
512 independent connections and control 128. An explicit fair semaphore prevents
a worker reusing a connection from repeatedly bypassing queued workers; the
first local fairness test reproduced that starvation without the semaphore.
Direct `poll()` calls retain their caller-requested wait. The 512-idle-worker
regression checks every worker gets served while at most 128 polls are active,
and cancellation clears worker accounting. Later live runs also measured
public relay health separately from gateway health.


## Idle relay connections after the first cycle

The fair-poll SDK candidate (`b59c959edf7b106e7cc9b1fadafb6fc62aea60ad`)
let all 512 calls reach the first upstream barrier, but the first wake/tool
cycle took 118.3 seconds. In the next cycle, parking took 137.2 seconds and
waiting for the last upstream calls another 64.0 seconds. Gateway health
remained available, while three public relay probes timed out at five seconds.
The run was intentionally interrupted and fully cleaned up; it is not a pass.

The relay had exactly 1024 established ingress connections. Of those, 531
had no TCP activity for over 60 seconds. Inspection of the pinned aiohttp
implementation found its default idle keepalive timeout was 3630 seconds.
Server 0.5.43 bounds idle keepalive to five seconds. This limit applies only
between requests; a socket-level regression verifies idle EOF while a
concurrent active request survives beyond that interval and completes normally.
No active model-call timeout or retry budget was shortened. Full checks passed
905 server tests (six skipped), 114 SDK tests, lint, Go/shell checks, builds
and installed-wheel verification.

[Retained interrupted run](../benchmarks/concurrency-512-0542-relay-idle-connections-2026-09-19.json).

## Gateway wake admission cost

The first 0.5.43 run passed all 285 gateway and 285 relay health probes, but
one of 512 callers missed the unchanged 120-second wake/tool deadline. It
cleaned up completely. Worker restore spans were approximately 0.3–0.5 seconds;
sampled gateway wake spans were 3.7–4.0 seconds, including roughly 0.11–0.13
seconds of thread CPU each. A local 512-route/four-worker profile showed
repeated fleet route reads and inventory decoding dominating wake admission.

0.5.44 narrows local capacity checks to fresh owner routes and inventory.
Incoming migration reservations still count, including CPU/RAM through routed
and activated phases. Portable wake placement and consolidation continue to
consider the fleet. Unpublished checkpoints, which can only wake locally, no
longer load unrelated nodes for shadow planning; impossible consolidation
also exits before a fleet scan. No TTL cache or stale admission state is used.
A 32-wake local profile dropped from 3.15 seconds to 1.23 seconds (61%); this
is a scheduling microbenchmark, not a production latency claim. Tests compare
owner admission against full fleet reservations across migration phases and
identity aliases, and prove local wakes read fresh state without a fleet scan.
