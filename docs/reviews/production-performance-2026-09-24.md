# Production traffic investigation, 24 September 2026

Read-only inspection around 11:25–11:34 UTC. No deployment, restart, configuration
change, profiler attachment, or generated workload. Recent metrics cover roughly
11:15–11:30 UTC; histogram quantiles are estimates, not exact request percentiles.

## Findings

The four-vCPU gateway experienced bursts of CPU contention: load reached 10 and
CPU PSI some avg10 reached 46%. A later one-second sample was 91% idle. Workers
had roughly 71–75 GB available RAM, 12–40% CPU, little I/O pressure, and no storage
waiters in the initial snapshot. By 11:31, cached worker inventories showed zero
sandboxes; gateway health returned in 11 ms and relay delivery pending was zero.
This does not establish why the workload stopped.

The clearest avoidable work is image-build polling:

* `_get_image_build` calls `_image_build_records_across_nodes`, fetching complete
  build lists from every ready builder to answer one build-status request.
* Every successful historical result goes through `_record_successful_build_image`:
  registry protection resolution, an unconditional image-store upsert, and image
  inventory invalidation. `ImageStore.upsert` opens a write transaction and uses
  INSERT OR REPLACE even for identical records.
* One sampled poll took 28.618 seconds and ended in BrokenPipeError. Four builder
  responses contained about 1.65 MB in total. Their response-header spans totaled
  about 0.66 seconds; the trace does not separately attribute the remaining time
  to SQLite, registry enrichment, scheduling, or other local work.
* A sampled create took 34.733 seconds: image resolution consumed 31.500 seconds,
  placement 0.629 seconds, and image warmup waiting 2.002 seconds. Name resolution
  uses a shared inventory cache whose cold loader queries nodes sequentially.
  Repeated build-result invalidation is a concrete mechanism for forcing refreshes;
  these traces do not quantify its share of total gateway CPU.

The first recent metrics snapshot estimated create p95 at 8.45 seconds. File
upload p95 was 13.25 seconds versus 0.227 seconds for the nested write operation.
These separate histogram populations cannot be subtracted. The upload parent
includes request-body reception; inspect `upload.receive_ms` on matched traces
before changing storage code or assuming disk is responsible.

Recorded completed wake coordination in the preceding 15 minutes: 5,734 distinct
requests, median 0.140 seconds, p95 0.419 seconds, max 3.868 seconds; 150 exceeded
one second. These are control-plane completion timings, not proof of guest-visible
continuation latency or full-RAM restore performance. Lifecycle error events
included superseded parks and busy retries, not necessarily failed requests.

A sampled 69.14-second relay HTTP 503 had a durable result status of 503. The
result was committed about 67.95 seconds after enqueue, then released about 1.17
seconds later. Wake completed on its first attempt. This particular 503 was in the
submitted result, not generated by wake failure. Its ultimate source remains
unverified. Relay request duration includes waiting for the external model worker.

## Recommended implementation order

1. Make build-result observation idempotent: compare stored image state, avoid
   unchanged writes, and invalidate image inventory only on meaningful changes.
   Preserve registry digest protection and generation fences.
2. Route individual build-status requests to their owner, with bounded discovery
   fallback for unknown owners; retain terminal results locally. Do not fetch and
   reprocess all builder histories on every poll.
3. Resolve known published managed images from canonical local metadata, keeping
   explicit refresh and completeness handling for misses. Avoid fleet-wide image
   inventory refresh on the common create path.
4. Add phase timing around build-list enrichment/store writes and matched upload
   receive/write phases before further tuning. Use bounded existing telemetry;
   do not bulk-fetch traces on the small production telemetry container.

Validate repeated concurrent polls produce no unchanged image writes or cache
invalidations, only query the owning builder, preserve replacement/deletion and
unknown-owner behavior, and do not delay unrelated sandbox creation. Then compare
the same workload's gateway CPU, create tails, and client-visible errors. No
additional worker capacity or language rewrite is justified by these snapshots.

## Local implementation

Implemented the first two targets without changing production:

* Image observation compares the serialized record in a read transaction first.
  Changed observations recheck under the writer lock before committing, so
  concurrent identical results produce one change. Unchanged polls neither
  write nor invalidate the inventory cache. Digest protection still runs.
* Single-build polling uses the existing single-build endpoint. Exact build IDs
  learn a bounded owner hint checked against job, node, and node epoch. Missing
  or failed owners fall back to discovery. No build status is cached, and image
  names still inspect all builders to select the latest build. Discovery reads
  only the requested record rather than every historical record.

The seven new regression tests cover concurrent no-op observations, concurrent
initial writes, changed/deleted image observations, inventory invalidation,
concurrent owner polling, owner failure/restart fallback, latest-by-name lookup,
and unrelated/unknown results. Alongside the existing image, control-plane, and
inventory-cache tests, 116 tests pass locally. Ruff and diff whitespace checks
pass. Production performance and deployment qualification remain outstanding.

The broader canonical image-name lookup change is deferred: avoiding needless
cache invalidation first removes a known source of refreshes without changing
image visibility or deletion semantics.

## Client failure attribution correction

The user's runner attributed the job termination to two shared image-build
polling timeouts, each affecting eight waiting rollouts; one build subsequently
succeeded. Treat this as two shared dependency failures affecting 16 rollouts,
not 16 independent provisioning failures. The generic provisioning wrapper hid
the failing API phase. The runner/monitor attribution was supplied by the user,
not independently reconstructed from the gateway traces.

The SDK's sync and async build wait loops previously propagated transport
timeouts immediately. Local SDK changes now retry only status GETs with jitter,
honoring the original overall deadline and Retry-After. A regression reproduces
eight waiters sharing one async build wait through transient polling failures.
No build POST is replayed. The external runner's correlated-failure reporting
has not been changed.

SDK validation: 76 focused client/Inspect/polling tests pass, and wheel/source
builds and lint pass. The full suite ran 144 tests with one error in the existing
512-upstream keepalive test (local connection failures followed by a readiness
timeout). That same error reproduced with the committed, unmodified client in
an isolated baseline package. These changes have not been released or deployed.
